## 알림 시스템 구현 (1)
### 트랜잭션 경계와 실행 시점의 정합성 문제

---

## 0. 이 글에서 다루는 것

프로젝트에 알림 기능을 구현해 보면서 겪은 사고 과정을 남긴다.  
1편에서 다루는 주제는 **트랜잭션 경계와 알림 실행 시점의 정합성**이다.

AOP `@AfterReturning` 과 `@TransactionalEventListener(AFTER_COMMIT)` 의 실행 시점 차이  
그리고 그에 따른 설계 전환을 정리했다.

---

## 1. 알림 서비스의 요구사항

알림은 대략 이런 시점에 발생한다.

- 룸메이트 신청이 들어왔을 때
- 신청이 수락/거절되었을 때
- 채팅 메시지가 도착했을 때
- 어떤 요청이 처리되었을 때

여기서 알림에 대한 요구사항은 다음과 같다.

- **R1. 알림은 성공한 비즈니스 결과에 대해서만 생성되어야 한다.**
    - 알림 시스템은 비즈니스 로직의 커밋을 보장받아야 한다.
- **R2. 비즈니스가 실패(롤백)하면 알림도 나가면 안 된다.**
- **R3. 알림을 보고 화면으로 들어오면 항상 DB에도 그 상태가 있어야 한다.**
- **R4. 알림 로직은 여러 비즈니스를 횡단하며, 비즈니스 코드를 최대한 훼손시키지 않았으면 좋겠다.**
    - 서비스/유스케이스 메서드 안이 알림 호출로 더러워지지 않았으면 했다.

이 요구사항들을 동시에 만족시키기 위해, 처음에는 **AOP + `@AfterReturning`** 이 적당해 보였다.

---

## 2. 첫 번째 시도 – AOP + `@AfterReturning` 으로 알림 보내기

### 2.1 왜 하필 `@AfterReturning` 이었나

당시에는 대략 이렇게 생각했다.

- `@Transactional` 메서드가 **정상적으로 종료**되면,
- 그 시점에는 대부분 **트랜잭션도 커밋되어 있을 것**이라고 직관적으로 믿었다.
- 그렇다면 `@AfterReturning` 에서 알림을 보내면,
    - “비즈니스가 성공한 뒤에”,
    - “커밋도 이미 된 상태에서”
    - 깔끔하게 알림을 보낼 수 있을 것 같았다.

여기에 앞에서 말한 **R4(비즈니스 코드 훼손 최소화)** 가 더해졌다.

- 서비스/유스케이스 메서드 안에 알림 호출을 잔뜩 넣기보다는
- 어노테이션과 AOP로 “이 메서드는 성공하면 알림을 보내라” 정도만 선언하고
- 실제 알림 로직은 Aspect 쪽으로 빼내고 싶었다.

그래서 대략 이런 구조를 떠올렸다.

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Notify {
    // 알림 타입, 템플릿 ID 같은 메타데이터
}
```

```java
@Service
public class ApplyRoomUseCase {

    private final RoomRepository roomRepository;
    private final UserRepository userRepository;

    @Notify
    @Transactional
    public void applyRoom(String roomId, String userId) {
        // 방/유저 검증
        // 중복 신청 여부 체크
        // 신청 엔티티 생성 및 저장
    }
}
```

```java
@Aspect
@Component
public class NotificationAspect {

    private final NotificationService notificationService;

    @AfterReturning("@annotation(Notify)")
    public void sendNotification(JoinPoint joinPoint) {
        // JoinPoint/파라미터에서 roomId, userId 등 추출
        // notificationService.send(대상 유저, "룸메이트 신청 완료", ...)
    }
}
```

머릿속 요약은 이랬다.

> 메서드가 정상 종료(@AfterReturning)했다 == 비즈니스가 성공했고   
> 그 시점에는 트랜잭션도 이미 마무리되었을 것이라고 판단했다.

하지만 실제 동작을 뜯어보니, 이 가정이 틀렸다는 걸 알게 됐다.

### 2.2 실제로 마주친 문제

테스트와 로그를 통해 이런 상황을 확인했다.

> 호출 스택
    ![AOP 트랜잭션 호출 스택.png](../assets/AOP%20%ED%8A%B8%EB%9E%9C%EC%9E%AD%EC%85%98%20%ED%98%B8%EC%B6%9C%20%EC%8A%A4%ED%83%9D.png)
로그
  ![AOP 트랜잭션 로그.png](../assets/AOP%20%ED%8A%B8%EB%9E%9C%EC%9E%AD%EC%85%98%20%EB%A1%9C%EA%B7%B8.png)

- `applyRoom()` 이 예외 없이 리턴되고,
- `@AfterReturning` 에서 알림도 잘 나갔다.
- 그런데 조금 뒤에 같은 트랜잭션 안에서 다른 예외가 발생하면서 **전체 트랜잭션이 롤백**되었다.
- 결과적으로:
    - 푸시는 “룸메이트 신청이 완료되었습니다” 라고 왔는데,
    - 방 신청 내역을 열어보면 **그 신청이 DB에는 없다.**

즉, R2, R3를 위반하는 상황이다.

여기서 의문이 생겼다.

> 메서드가 정상 리턴했는데, 왜 아직 커밋 전일 수 있지?  
> `@AfterReturning` 이랑 트랜잭션 커밋은 어떤 순서로 실행되는 거지?

이 의문을 풀려면, **Spring AOP와 트랜잭션 프록시의 생명주기**를 이해해야 했다.

## 3. 트랜잭션과 AOP의 생명주기 – `@AfterReturning` 이 너무 이른 이유

핵심은 "프록시가 어떻게 겹쳐져 있는가" 이다.

- `@Transactional` 은 **트랜잭션 프록시**를 만든다.
- 우리가 만든 `@Aspect` 도 또 다른 프록시를 만든다.
- 이 프록시들이 어떤 순서로 감싸는지에 따라
    - 실제 메서드 실행 시점
    - `@AfterReturning` 실행 시점
    - 트랜잭션 커밋 시점이 달라진다.

이제 트랜잭션과 AOP 내부 구현 구조를 따라가며  
트랜잭션과 AOP의 실행 시점이 어디에서 어긋났는지를 분석해보자.

### 3.1 단순화한 호출 흐름

대략 이런 흐름이라고 볼 수 있다.

```text
BusinessUseCase
  -> Spring AOP Proxy
     -> 알림 AOP MethodInterceptor
        -> TransactionInterceptor
           -> 트랜잭션 시작 (createTransactionIfNecessary)
           -> 실제 Service 메서드 실행 (invocation.proceed)
           <- Service 메서드 정상 리턴
           -> finally 블록에서 commit()/rollback()
        <- TransactionInterceptor 종료
        -> @AfterReturning 실행   // 알림 발송
     <- Proxy 종료
```

즉:

1. 실제 서비스 메서드는 트랜잭션 프록시 안에서 실행된다.
2. `@AfterReturning` 은 **대상 메서드가 예외 없이 리턴한 직후**에 실행된다.
3. 하지만 **트랜잭션 커밋/롤백은 그 이후** `finally` 블록에서 처리한다.

그래서 이런 문장이 성립한다.

> `@AfterReturning` 은 메서드 정상 종료만 보장할 뿐 **트랜잭션 커밋 완료를 보장하지 않는다.**

우리가 원했던 기준은 처음부터 **커밋이 확정된 뒤에만 알림을 보낸다** 였다.  
(`R2`, `R3` 요구사항)  
하지만 `@AfterReturning` 은 그보다 한 단계 이른 시점이었다.

> 참고로 AOP 어드바이저의 `@Order` 나 `@EnableTransactionManagement(order = …)` 를 이용해서
**트랜잭션 어드바이저보다 바깥쪽에 `@AfterReturning` 어드바이저를 배치**하면, 겉으로 보기에는
커밋 후에 알림이 실행되는 것처럼 보이게 만들 수도 있다. 하지만 이 방식은 기준이
"DB 커밋이 끝났는가" 가 아니라 **프록시 체인에서 어느 어드바이저가 먼저/나중에 `proceed()` 를 호출했는가** 에
달려 있어서, 구조적인 해결책이라기보다는 트릭에 가깝다고 판단했다.   
> 최종적으로는 트랜잭션 생명주기 자체 (`TransactionSynchronization` / `@TransactionalEventListener`)에 매달리는 쪽이 더 명시적이고 안전하다고 판단했다.

결론적으로 AOP 레벨에서 알림을 트랜잭션 커밋 이후로 미루기 어렵다는 걸 깨달았다.  
그래서 이제는 트랜잭션 수명주기 자체에 붙을 수 있는 메커니즘이 필요했다.

## 4. 해결 – 이벤트 발행 + `@TransactionalEventListener(AFTER_COMMIT)`

Spring은 이미 트랜잭션 생명주기에 맞는 훅을 제공하고 있다.  
그것이 `@TransactionalEventListener` 이고, `phase` 옵션으로 **AFTER_COMMIT** 을 줄 수 있다.

아이디어는 이렇게 바뀌었다.

- 유스케이스(트랜잭션 안)에서는 **알림을 직접 보내지 않는다.**
- 대신 **알림 요청 이벤트**를 발행한다.
- 이 이벤트를 AFTER_COMMIT 리스너에서 처리한다.

### 4.1 퍼블리셔 – 트랜잭션 안에서는 "이벤트만 던진다"

```java
@Component
@RequiredArgsConstructor
public class NotificationRequestPublisher {

    private final ApplicationEventPublisher eventPublisher;

    public void publish(...) {
        NotificationRequestEvent event = new NotificationRequestEvent(...);
        eventPublisher.publishEvent(event);
    }
}
```

`ApplyRoomUseCase` 에서는 이제 이렇게만 한다.

```java
@Service
@RequiredArgsConstructor
public class ApplyRoomUseCase {

    private final RoomRepository roomRepository;
    private final UserRepository userRepository;
    private final NotificationRequestPublisher notificationPublisher;

    @Transactional
    public void applyRoom(String roomId, String userId) {
        // 1. 방/유저 검증
        // 2. 중복 신청 여부 체크
        // 3. 신청 엔티티 생성 및 저장

        // 4. 트랜잭션 안에서는 "알림 요청 이벤트"만 발행
        notificationPublisher.publish(...);
    }
}
```

파라미터는 알림을 전송하기 위한 최소한의 메타데이터만 담고 있다.

### 4.2 리스너 – AFTER_COMMIT 에서만 알림 처리

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class NotificationRequestListener {

    private final NotificationService notificationService;
    private final UserDeviceTokenRepository deviceTokenRepository;
    private final NotificationDeliveryOrchestrator deliveryOrchestrator;

    @Transactional
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void handle(NotificationRequestEvent event) {
        // 1. 알림 엔티티 저장
        Notification notification = notificationService.save(event);

        // 2. 등록된 모든 기기에 알림 전달
        List<Device> devices =
                deviceTokenRepository.findDevicesByUser(notification.getRecipientId());

        for (Device device : devices) {
            deliveryOrchestrator.deliver(notification, device);
        }
    }
}
```

여기서 실행 시점과 관련해 중요한 포인트는 두 가지다.

- **`@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`**
    - 이 리스너는 이 이벤트를 발행한 트랜잭션이 **성공적으로 커밋된 후**에만 실행된다.
    - 트랜잭션이 롤백되면, 리스너는 **아예 실행되지 않는다.**
- **`@Transactional`**
    - 리스너 내부 작업(알림 저장 + 전송)은 원래 비즈니스 트랜잭션과는 분리된 새로운 트랜잭션 안에서 수행된다.
    - 그래서 알림 처리 도중 예외가 나더라도 앞서 커밋된 비즈니스 데이터는 영향을 받지 않는다.

이 구조 덕분에 요구사항을 이렇게 만족시킬 수 있다.

- **R1**: 비즈니스가 성공하면(커밋되면) AFTER_COMMIT 리스너가 실행되면서 알림 저장 및 발송한다.
- **R2**: 비즈니스가 실패(롤백)하면 리스너가 호출되지 않으므로 알림도 나가지 않는다.
- **R3**: 사용자가 알림을 타고 들어왔을 때, 이미 비즈니스 트랜잭션이 커밋된 이후이므로 항상 DB에서 해당 상태를 조회할 수 있다.
- **R4**: 비즈니스 코드 안에는 퍼블리셔 한 줄 정도만 남으므로, 도메인 로직이 지저분해지지 않는다.

## 5. `@AfterReturning` vs `AFTER_COMMIT` 정리

여기까지의 내용을 한 번에 요약해보면 다음과 같다.

- **`@AfterReturning`**
    - 기준: 대상 메서드가 **예외 없이 리턴**했는가?
    - 트랜잭션과의 관계:
        - 타겟 메서드 실행이 정상 종료된 직후 실행된다.
        - 트랜잭션 커밋이 완료되었는지는 보장하지 않는다.
        - 트랜잭션 경계와 직접적으로 동기화되어 있지 않다.
    - 적합한 용도:
        - **메서드 성공 여부**에만 관심 있는 횡단 관심사

- **`@TransactionalEventListener(AFTER_COMMIT)`**
    - 기준: 이 이벤트를 발행한 트랜잭션이 **정상 커밋**되었는가?
    - 트랜잭션과의 관계:
        - 커밋이 실제로 성공한 이후에만 실행된다.
            - 롤백 시에는 호출되지 않는다.
            - 트랜잭션 동기화 메커니즘(TransactionSynchronization)에 의해 제어된다.
    - 적합한 용도:
        - “최종 커밋된 상태”와 정합성이 맞아야 하는 외부 IO

이 프로젝트의 알림 요구사항(R1~R4)을 다시 보면 처음부터 우리가 필요로 했던 건

> 메서드가 성공했는지가 아니라 **트랜잭션이 실제로 커밋됐는지** 였다.

1차 시도에서는 이 둘을 같다고 생각해서 AOP + `@AfterReturning` 으로 갔다가  
Spring 내부 구조를 조금 더 들여다본 뒤에야 둘을 명확히 구분하게 되었다.

## 6. 마무리 – 비슷한 상황에서 던져볼 체크리스트

마지막으로, 비슷한 상황에서 스스로에게 던져볼 만한 질문들을 정리하고 마친다.

- **Q1. 이 기능은 트랜잭션 롤백 시 함께 사라져야 하는가?**
    - 그렇다면 최소한 **AFTER_COMMIT 이후**에 실행되어야 한다.
- **Q2. 지금 설계는 "메서드 성공"을 기준으로 하나, "커밋 완료"를 기준으로 하나?**
    - AOP의 `@AfterReturning` 은 전자,
    - `@TransactionalEventListener(AFTER_COMMIT)` 은 후자다.
- **Q3. 비즈니스 코드가 알림 로직 때문에 지저분해지고 있지 않은가?**
    - 이벤트 퍼블리셔 + AFTER_COMMIT 리스너 패턴은 정합성, 관심사 분리, 테스트 용이성을 동시에 어느 정도 충족시켜 준다.

1편에서는 이렇게 **트랜잭션 경계와 실행 시점의 정합성**이라는 관점에서  
AOP → 트랜잭션 내부 구조 이해 → AFTER_COMMIT 이벤트 패턴으로 넘어간 과정을 정리했다.

2편에서는 여기서 한 발 더 나아가서

- 왜 “외부 IO는 아예 트랜잭션 밖으로” 빼야 하는지
- 이를 위해 어떤 구조(예: 큐/아웃박스/별도 컨슈머)를 고려했는지

를 구체적인 패턴과 함께 이야기해보겠다.
