# 스프링에서 트랜잭션이 동작하는 과정

앞에서 `@Transactional`이 AOP 기반으로 동작한다는 것을 확인했다.

하지만 실제로 트랜잭션을 시작하고(commit) 종료(rollback)하는 주체는 프록시가 아니다.

이 글에서는 스프링 트랜잭션의 핵심 엔진인 TransactionManager를 중심으로,  
트랜잭션이 내부적으로 어떤 계층을 거쳐 동작하는지 끝까지 따라가 본다.

---

## 1. 트랜잭션 처리 콜스택 흐름 (@Transactional)

```less
Service 메서드 호출 (실제론 프록시 호출)
  └── AOP Proxy (CGLIB/JDK).invoke()
        └── ReflectiveMethodInvocation.proceed()
              └── TransactionInterceptor.invoke()
                    └── TransactionAspectSupport.invokeWithinTransaction()
                          ├── createTransactionIfNecessary()
                          │     └── PlatformTransactionManager.getTransaction(...)
                          │           └── AbstractPlatformTransactionManager.getTransaction(...)
                          │                 ├── doGetTransaction()                 // 트랜잭션 객체/자원 조회
                          │                 ├── isExistingTransaction(tx)          // 기존 트랜잭션 존재 여부 판단
                          │                 ├── handleExistingTransaction(...)     // 전파 옵션 분기(참여/신규/중단 등)
                          │                 │     ├── suspend(...)                    // (REQUIRES_NEW, NOT_SUPPORTED 등)
                          │                 │     └── resume(...)                     // 중단된 트랜잭션 복구
                          │                 └── startTransaction(...)              // 신규 트랜잭션 시작
                          │                       └── doBegin(...)                    // 구현체에서 실제 begin
                          │
                          ├── invocation.proceedWithInvocation()
                          │     └── (실제 Service 메서드 실행)
                          │
                          ├── (정상 종료 시)
                          │     └── commitTransactionAfterReturning()
                          │           └── PlatformTransactionManager.commit(...)
                          │                 └── AbstractPlatformTransactionManager.commit(...)
                          │                       ├── processCommit(...)           // 커밋 흐름 제어
                          │                       └── doCommit(...)                // 구현체에서 실제 commit
                          │
                          ├── (예외 발생 시)
                          │     └── completeTransactionAfterThrowing()
                          │           └── PlatformTransactionManager.rollback(...)
                          │                 └── AbstractPlatformTransactionManager.rollback(...)
                          │                       ├── processRollback(...)         // 롤백 흐름 제어
                          │                       └── doRollback(...)              // 구현체에서 실제 rollback
                          │
                          └── cleanupTransactionInfo()
                                ├── TransactionSynchronizationManager.unbindResource(...)
                                └── cleanupAfterCompletion(...)                    // 동기화/자원 정리
```
이 흐름을 단계별로 따라가 보자.

---

## 2. 프록시: 트랜잭션 경계를 여는 호출 경로

`@Transactional`이 붙은 클래스는 실제 객체 대신 **프록시 객체**로 등록된다.

따라서 메서드를 호출하면:

```
Service → Proxy → Interceptor 체인
```

으로 진입한다.

프록시는 트랜잭션을 직접 실행하지 않는다.  
단지 **`TransactionInterceptor`에게 제어권을 넘긴다.**

즉, 프록시는 실행자가 아니라 **트랜잭션 경계**를 만드는 역할이다.

---

## 3. TransactionInterceptor: 트랜잭션 AOP 진입점

```java
TransactionInterceptor.invoke(...)
```

이 클래스는 트랜잭션 처리를 직접 수행하지 않는다.  
실제 로직은 부모 클래스 `TransactionAspectSupport`에 있다.

여기서부터 트랜잭션 처리 시나리오가 시작된다.

---

## 4. invokeWithinTransaction(): 트랜잭션 시나리오의 중심

```java
TransactionAspectSupport.invokeWithinTransaction(...)
```

이 메서드는 트랜잭션의 전체 생명주기를 관리한다.

하는 일은 크게 네 단계다.

1. 트랜잭션 시작 여부 결정
2. 실제 메서드 실행
3. 정상 종료 시 commit
4. 예외 발생 시 rollback

이 구조는 결국 try-catch-finally 패턴으로 이루어져 있다.

---

## 5. 트랜잭션 시작 과정

트랜잭션 시작은 다음 흐름에서 일어난다.

```
createTransactionIfNecessary()
   ↓
PlatformTransactionManager.getTransaction()
   ↓
AbstractPlatformTransactionManager.getTransaction()
```

---

### 5.1 doGetTransaction()

현재 스레드에 바인딩된 트랜잭션 자원을 조회한다.  
스프링은 트랜잭션을 **[ThreadLocal](../java/ThreadLocal.md) 기반으로 관리**한다.

```
ThreadLocal
  └─ 현재 스레드에 묶인 Connection / EntityManager
```

이 단계는 **이미 트랜잭션 안에 있는지**를 확인하기 위한 준비 단계다.

---

### 5.2 isExistingTransaction()

기존 트랜잭션이 활성화되어 있는지 판단한다.  
여기서 **참여할지/새로 만들지**의 1차 분기가 일어난다.

---

### 5.3 handleExistingTransaction()

[트랜잭션 전파(Propagation)](Spring%20%ED%8A%B8%EB%9E%9C%EC%9E%AD%EC%85%98%20%EC%A0%84%ED%8C%8C.md)옵션에 따른 전략 분기가 일어난다.

예:

- REQUIRED → 기존 트랜잭션에 참여
- REQUIRES_NEW → 기존 트랜잭션 suspend 후 새 트랜잭션 시작
- NOT_SUPPORTED → 기존 트랜잭션 suspend
- NEVER → 예외 발생

여기서 중요한 개념은 다음이다.

> 전파는 단순한 조건 분기가 아니라  
> ThreadLocal에 묶인 자원을 교체하거나 유지하는 전략이다.

---

### 5.4 startTransaction() → doBegin()

기존 트랜잭션이 없으면 신규 트랜잭션을 시작한다.

```less
startTransaction()
   └── doBegin()
```

`doBegin()`은 구현체에서 실제 DB 트랜잭션을 시작하는 지점이다.

예 (JDBC 기반):

- Connection 획득
- autoCommit = false 설정
- `TransactionSynchronizationManager`에 자원 바인딩

이 시점부터 트랜잭션 경계가 형성된다.

---

## 6. 비즈니스 로직 실행

```
invocation.proceedWithInvocation()
```

이 단계에서 실제 서비스 메서드가 실행된다.

이미 트랜잭션이 시작된 상태이므로  
이 안에서 발생하는 모든 DB 작업은 같은 트랜잭션에 묶인다.

---

## 7. commit 흐름

정상 종료 시:

```
PlatformTransactionManager.commit()
   └── doCommit()
```

하지만 여기서 중요한 점이 있다.

- 신규 트랜잭션이면 실제 commit 수행
- 기존 트랜잭션에 참여한 경우라면 실제 commit은 수행되지 않음

왜냐하면 상위 트랜잭션이 최종 결정권을 가지기 때문이다.

---

## 8. rollback 흐름

예외 발생 시:

```
PlatformTransactionManager.rollback()
   └── doRollback()
```

참여 트랜잭션일 경우에는 실제 rollback 대신  
**rollback-only 마킹**만 수행한다.

그래서 이런 현상이 발생한다.

> 내부 메서드에서 예외가 발생하면  
> 외부에서 commit을 호출하더라도 최종 결과는 rollback이 된다.

---

## 9. cleanup: 트랜잭션은 어떻게 정리되는가

트랜잭션은 commit/rollback으로 끝나지 않는다.  
반드시 정리가 필요하다.

콜스택상 마지막 단계는 다음이다.

```
cleanupTransactionInfo()
   └── TransactionSynchronizationManager.unbindResource(...)
```

cleanup이 하는 일은 다음과 같다.

- ThreadLocal에 바인딩된 자원 해제
- 트랜잭션 상태 정보 정리
- suspend된 이전 트랜잭션이 있다면 resume
- 동기화 콜백(afterCompletion 등) 정리

이 과정이 없다면 스레드 풀 환경에서  
이전 요청의 트랜잭션 문맥이 다음 요청으로 전파될 수 있다.

따라서 트랜잭션의 진짜 종료는 **commit/rollback + cleanup**이다.

---

## 10. 정리

스프링 트랜잭션은 다음 계층이 협력하여 동작한다.

- 프록시: 트랜잭션 경계를 만든다.
- `TransactionInterceptor`: AOP 진입점.
- `TransactionAspectSupport`: 트랜잭션 처리 시나리오 실행.
- `PlatformTransactionManager`: 트랜잭션 추상화.
- `AbstractPlatformTransactionManager`: 전파 전략 및 실행 분기 담당.
- `TransactionSynchronizationManager`: ThreadLocal 기반 자원 관리.

결국 `@Transactional`은 단순한 애노테이션이 아니라,

> AOP + 추상화된 트랜잭션 매니저 + ThreadLocal 자원 바인딩  
> 이 세 가지가 결합된 메커니즘이다.
